# OpenClaw × 玄关知识库同步 — 业务说明

> 本文面向产品、运维、业务负责人及首次接触本项目的协作者，说明**这个项目解决什么问题、在什么场景下使用、以及系统如何运转**。  
> 部署与接口细节见 [README.md](../README.md)、[MANAGEMENT_API.md](./MANAGEMENT_API.md)；技术架构见 [DESIGN.md](./DESIGN.md)。

---

## 1. 项目是什么

**openclaw-xgkb-sync** 是一个运行在 OpenClaw 节点上的**后台同步服务**，负责把 Agent 在本地工作区产出的文件，与**玄关知识库（XGKB）**云端目录保持同步。

可以把它理解成：

- **OpenClaw 的「文件出口」**：Agent 写 Markdown、报告、笔记等到本地目录，本服务自动推到知识库，供人在网页端检索、协作、归档。
- **知识库的「本地镜像」**（可选）：在双向或仅下载模式下，云端已有文档也会拉回本地，供 Agent 继续读写。
- **多用户、多目录的批量同步枢纽**：一台或多台服务器上可配置大量「本地目录 ↔ 云端目录」映射，各自独立运行，互不干扰。

**不依赖 Obsidian 等桌面客户端**，以 Node.js 常驻进程方式运行，适合服务器、沙箱、CI 环境等「无 GUI」场景。

---

## 2. 解决什么问题

| 痛点 | 本项目的做法 |
|------|----------------|
| Agent 产出只在本地，业务方看不到 | 定时或手动同步到知识库固定目录，形成可共享的知识资产 |
| 多人、多 Agent、多工作区，目录结构复杂 | 用 **Mapping（映射）** 为每个本地根目录指定云端目标路径与同步策略 |
| 全量上传浪费带宽、易触发 API 限流 | **增量优先**：只处理有变化的文件；周期性全量对账兜底一致性 |
| 本地与云端可能同时改同一文件 | **LWW（Last Write Wins）**：以修改时间较新的一方为准，冲突有明确规则 |
| 运维需要远程增删映射、看状态 | 内置 **Web 控制台** 与 **HTTP 管理 API**，支持热重载配置 |
| 数百用户各自用不同 AppKey | **按 AppKey 独立限速**，多用户并行时不互相抢配额 |

## 3. 典型使用场景

### 3.1 个人助理：Agent 输出归档到知识库

- **本地**：OpenClaw 沙箱下的 `workspace/out/` 等目录，Agent 生成 `.md` 报告、会议纪要、任务总结。
- **云端**：知识库个人空间下的 `AgentOutput/张三/`。
- **方向**：多为 **push（仅上传）**，本地为准，云端只读归档。

### 3.2 双向协作：本地编辑与云端修订并存

- 业务人员在知识库网页端修改文档，Agent 在本地继续加工同一批文件。
- **方向**：**bidirectional（双向）**，按最后修改时间自动合并；适合需要「人机共编」的知识区。

### 3.3 从知识库拉取参考材料

- Agent 启动前需要从知识库拉取规范、模板、历史案例。
- **方向**：**pull（仅下载）**，以云端为准更新本地。

### 3.4 大规模多租户：一机多 Mapping

- 云端部署多个 OpenClaw 实例，每个用户/每个 Agent 一条 Mapping。
- 每条 Mapping 可使用**独立 AppKey**（对应各自的知识库授权），限速互不影响。
- 通过管理 API 或控制台批量增删用户映射，无需重启整个平台（配置热重载）。

## 4. 核心概念

### 4.1 同步映射（Mapping）

一条 Mapping 表示**一对目录的同步关系**：

| 概念 | 业务含义 |
|------|----------|
| `localRoot` | 本地绝对路径，Agent 文件实际落盘位置 |
| `remoteRootFolderPath` | 知识库内的逻辑路径，如 `OpenClaw/OutputA`；不存在时会**自动创建** |
| `projectId` | 知识库「空间」；不填则使用**个人空间** |
| `appKey` | 调用知识库 Open API 的身份凭证；可全局统一，也可按 Mapping 单独配置 |
| `syncDirection` | `push` / `pull` / `bidirectional` |
| `filePatterns` | 只同步匹配的文件（默认 `**/*.md`） |

同一进程可配置**多条 Mapping**，例如：任务 A 输出、任务 B 输出、团队共享区各一条。

### 4.2 同步方向

| 模式 | 行为 | 适用 |
|------|------|------|
| **push** | 只上传、只删远端多余文件 | Agent 产出归档 |
| **pull** | 只下载、只删本地多余文件 | 以云端为源头的模板/规范同步 |
| **bidirectional** | 两端变更互相同步，冲突按时间戳 | 人机共编、双向迭代 |

### 4.3 身份与空间

- **AppKey**：玄关开放平台签发，决定「以谁的身份」访问知识库 API。
- **空间（projectId）**：知识库内的项目/个人空间；不配置时自动解析为当前 AppKey 对应的个人空间。
- **远端根路径**：Mapping 只同步该路径下的子树，避免误扫整个空间。

## 5. 系统怎么运转（业务视角）

### 5.1 整体架构

```
┌─────────────────┐         Open API          ┌──────────────────┐
│  OpenClaw 节点   │  ◄──────────────────────►  │  玄关知识库 XGKB  │
│  本地工作区目录   │   上传 / 下载 / 列表 / 删除   │  云端目录与文件   │
└────────┬────────┘                             └──────────────────┘
         │
         │  扫描、决策、执行
         ▼
┌─────────────────┐
│  同步 Agent      │  ← config.json（映射与策略）
│  (本 Node 服务)  │  ← SQLite 状态库（水位与文件记录）
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  Web 控制台      │  健康检查、状态、增删 Mapping、触发同步
│  HTTP 管理 API   │
└─────────────────┘
```

### 5.2 一轮同步在做什么

对**每一条已启用的 Mapping**，服务按配置的间隔（默认约 3 分钟）或人工触发，执行大致如下步骤：

1. **准备远端上下文**  
   解析空间 ID、远端根目录 ID；若配置了路径但云端尚无该文件夹，则逐级创建。

2. **收集本地变更**  
   递归扫描 `localRoot`，找出新增、修改、删除的文件（相对路径 + 修改时间）。

3. **收集远端变更**  
   - 平时走**增量**：向知识库询问「自上次成功同步以来变了什么」。  
   - 首次同步、增量失败或到达全量对账周期时，走**全量扫描**兜底。

4. **逐文件决策**  
   对比本地、远端、以及 SQLite 里上一轮留下的记录，为每个文件决定：跳过、上传、下载、删本地、删远端等。  
   若两端都改过，**修改时间更晚的一方获胜**（LWW）。

5. **执行并记状态**  
   按「先删、再下、再上」顺序执行；成功则更新 SQLite 中的文件状态与**同步水位**；若有文件失败，水位不推进，下轮会重试。

6. **汇报结果**  
   管理 API / 控制台可查看每条 Mapping 的最近成功时间、错误信息、统计摘要。

**无变更时的优化**：若增量显示远端无变化，且本地也无新增/修改/删除，整轮可在毫秒级结束，几乎不消耗 API 配额。

### 5.3 调度与并发

- 多条 Mapping 可**并行**同步，并发数可自动或手动配置。
- 同一 Mapping 同时只会跑一轮同步；连续触发会合并为「待执行」，避免重复劳动。
- 每个 AppKey 有独立的**令牌桶限速**，避免打爆知识库 API；收到限流响应时会冷却一段时间再试。

### 5.4 配置如何生效

- 主配置在 **`config.json`**：全局策略 + Mapping 列表。
- 通过 **Web 控制台** 或 **HTTP API** 修改 Mapping 后，会自动写回配置文件并**热重载**，一般无需重启进程。
- 敏感信息（AppKey）不会通过 API 明文回显；修改时需重新填入才会覆盖。

## 6. 文件变更的业务语义

系统以**路径**识别文件，不识别操作系统级的「重命名事件」。业务上常见情况如下：

| 用户操作 | 系统理解 | 典型结果（push/双向） |
|----------|----------|------------------------|
| 本地新建文件 | 新路径 | 上传到云端 |
| 本地修改内容 | 同路径，mtime 更新 | 覆盖上传 |
| 本地删除文件 | 路径消失 | 删除云端对应文件 |
| 本地重命名 | 旧路径消失 + 新路径出现 | 删云端旧文件 + 上传新文件 |
| 云端网页端修改 | 远端 mtime 更新 | 拉回本地（pull/双向） |
| 两端同时修改 | 冲突 | 修改时间较新者覆盖另一方 |

周期性**全量对账**（默认约 1 小时）用于纠正增量遗漏或路径漂移，保证长期一致。

## 7. 运维与管理

### 7.1 日常操作

| 操作 | 方式 |
|------|------|
| 查看服务是否存活 | `GET /health` 或控制台概览 |
| 查看各 Mapping 同步情况 | `GET /status` 或控制台「运行状态」 |
| 新增/修改/禁用 Mapping | Web 控制台或 `POST/PUT /mappings` |
| 立即同步 | 「全部同步」或 `POST /sync`、`POST /sync/:mappingId` |
| 改完全局间隔、限速等 | 控制台「全局配置」或 `PUT /config` |

### 7.2 部署形态

- **单机单实例**：一台 OpenClaw 服务器跑一个同步 Agent，几条 Mapping 即可。
- **单机多 Mapping**：数百用户时，同一进程管理大量 Mapping，每用户独立 AppKey。
- **多机多实例**：多台服务器各跑一份 Agent，同步到同一或不同知识库空间；共用 AppKey 时需分摊限速配额。

进程以 **Node.js ≥ 18** 运行，状态落在本地 **SQLite** 文件，无额外数据库依赖。

### 7.3 安全注意

- `config.json` 含 AppKey，**不得提交代码仓库**。
- 管理 API 默认监听 `0.0.0.0:9090`，**无 HTTP 鉴权**，仅适合内网或本机；公网暴露需防火墙隔离或改绑 `127.0.0.1`。

## 8. 成功标准（业务验收）

部署与 Mapping 配置完成后，可从业务侧确认：

1. 服务持续运行，`/health` 返回正常，且至少有一条启用的 Mapping。
2. 在本地 `localRoot` 放入符合 `filePatterns` 的测试文件，触发同步后，知识库对应 `remoteRootFolderPath` 下可见该文件。
3. `/status` 中该 Mapping 的 `lastSuccessAt` 更新，且无持续性的 `lastError`。
4. （若双向）在云端修改后，下一轮同步本地文件内容随之更新。

## 10. 一句话总结

**openclaw-xgkb-sync 把 OpenClaw Agent 本地工作区与玄关知识库之间的文件同步自动化、可配置、可规模化**——通过 Mapping 定义「哪块本地目录对应云端哪条路径、往哪边同步、同步哪些文件」，在后台增量执行，并提供 Web 与 API 供运维与自动化管理。

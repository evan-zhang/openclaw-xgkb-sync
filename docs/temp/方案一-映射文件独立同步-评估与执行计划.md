# 方案一评估与执行计划：映射文件独立同步

> 基于 [方案一-映射文件独立同步.md](./方案一-映射文件独立同步.md) 与当前 `openclaw-xgkb-sync` 实现（2026-05）的对照评估。

---

## 1. 需求理解（摘要）

**问题**：Push 端（远程服务器）在 SQLite 中维护 `localPath → remoteFileId`，Pull 端（用户电脑）无法访问该 DB，Obsidian 等消费方无法按 fileId 精确拉取/关联文件。

**目标**：在同步链路中自动流转一份**轻量 JSON 索引**，使 Pull 端本地获得路径到 `remoteFileId` 的映射，且**不污染**现有 SyncEngine 路径对账逻辑。

```
服务器（push + enableFileIndex）→ 知识库根目录 `.openclaw-sync-map.json` → 用户（pull + enableFileIndex）→ 本地同名文件
```

---

## 2. 总体结论

| 维度 | 结论 |
|------|------|
| **是否合理** | **合理**。独立通道、不参与 `sync_file_state`、不参与 inode/路径对账，与当前架构一致 |
| **是否可行** | **可行**；**v1 已实现**（`fileIndexService.ts` + Web UI） |
| **工作量** | 原估 ~165 行偏乐观；含配置/UI/迁移/测试，建议按 **2～3 人日** 规划 |
| **与 Obsidian 关系** | 本方案只解决「索引如何到用户本地」；Obsidian 插件**另需**读取 JSON 并接入业务（不在本仓库范围） |

---

## 3. 已确认设计决策（2026-05-25）

| 议题 | 结论 |
|------|------|
| **serverId** | **不引入**。代码库中原本无此概念；JSON 内用现有 **`mappingId`** 标识来源即可 |
| **索引文件名** | 固定 **`.openclaw-sync-map.json`**（每个 mapping 的远端/本地根目录各一份） |
| **多服务器同根目录** | 接受后写覆盖；暂不处理 |
| **配置开关** | 仅 **`enableFileIndex?: boolean`**（mapping 级，默认 false） |
| **行为推导** | 由 `syncDirection` 决定 consume/publish，无需额外开关 |
| **上传 API** | **`uploadContent`**（小 JSON，不走 FileUploader）；**同目录+projectId+文件名幂等**，publish 无需事先查 fileId |

### 3.1 行为规则（单开关）

`enableFileIndex === true` 时：

| syncDirection | 同步开始前 | 同步成功后（`failed === 0`） |
|---------------|------------|------------------------------|
| `push` | — | publish |
| `pull` | consume | — |
| `bidirectional` | consume | publish |

> bidirectional 用户端可能用不完整 SQLite 覆盖服务器索引——**已知、可接受**；若后续出问题再加 publish 开关。

### 3.2 JSON 标识字段

不新增全局 `serverId`，索引 payload 示例：

```json
{
  "version": 1,
  "mappingId": "test",
  "updatedAt": "2026-05-25T10:00:00.000Z",
  "files": {
    "notes/foo.md": "remoteFileId123"
  }
}
```

Obsidian 消费端按 **`{localRoot}/.openclaw-sync-map.json`** 读取；多 mapping 时每个 vault/根目录各自一份。

### 3.2.1 索引粒度选型：根目录全量 vs 每目录一份

v1 **采用方案 A**。下列对比供评审与 Obsidian 侧对齐；结论应一目了然：**只需根目录一份全局索引**。

#### 方案 A：mapping 根目录一份全量索引（✅ v1 采用）

```
{localRoot}/
  .openclaw-sync-map.json          ← 唯一索引；files 含整棵子树
  notes/2024/foo.md
  notes/2024/bar.md
  项目/设计/v2.md
```

JSON 内键仍为**相对 mapping 根**的 `local_path`（如 `notes/2024/foo.md`），不是相对当前子目录的文件名。

#### 方案 B：每个目录各放一份「本目录索引」

```
{localRoot}/
  .openclaw-sync-map.json          ← 仅根下直属文件？
  notes/
    .openclaw-sync-map.json        ← 仅 notes/ 下文件
    2024/
      .openclaw-sync-map.json      ← 仅 2024/ 下文件
      foo.md
```

（具体命名可约定；本质都是 **O(目录数)** 个索引文件，每个只描述该目录一层或该子树。）

---

#### 全维度对比

| 维度 | 方案 A：根目录全量 | 方案 B：每目录一份 |
|------|-------------------|-------------------|
| **索引文件数量** | 每个 mapping **1** 个（本地 + KB 各 1） | 与**目录数**成正比；100 个目录 ≈ 100 个索引文件 |
| **Publish API 次数/轮** | 内容有变时 **1** 次 `uploadContent` | 变更分散在多个目录时，需 **多次** upload（或每轮扫全树找要更新的目录索引） |
| **Consume API 次数/轮** | Pull 端 **1** 次下载（有 cached fileId 时 1 次 `getDownloadInfo`） | 需 **N** 次下载，或先 list 所有目录索引再逐个拉 |
| **Pull 冷启动 locate** | 根目录 **1** 次 `getChildFiles` 找 1 个 fileId | 需发现 **所有** 目录下的索引文件（list 子树或递归扫目录） |
| **DB 状态** | `index_file_remote_id` **1** 个字段 | 需 **目录→fileId** 映射表（新表或 JSON blob），与 `sync_folder_state` 纠缠 |
| **实现复杂度（sync 服务）** | 一个 `fileIndexService`：SQLite 全量导出 → 一次 diff → 一次 upload | 按目录切分导出、按目录 diff、按目录 upload；目录增删要维护索引文件清单 |
| **Obsidian 消费** | 读 **1** 个 JSON → `map.files[file.path]` | 由 `file.path` 反查所在目录 → 再读该目录索引 → 或启动时合并 N 个 JSON |
| **内存/解析** | 一次 `JSON.parse`（万级约 1MB 内，可接受） | N 次 parse + 合并 Map；或每次查表先算目录路径 |
| **查表逻辑** | `id = map.files[path]`，O(1) | `id = mapDir[parentDir(path)][basename(path)]` 或合并后 O(1)，但前置成本高 |
| **单文件体积** | 随文件总数线性增（§5.5 可接受） | 单文件小，但 **总字节数相近**（元数据重复 N 份：version、mappingId、updatedAt…） |
| **内容 diff / 跳过无变更 upload** | 对整个 JSON 算 **1** 个 hash | 需对每个目录索引分别 hash；某目录 1 个文件变 → 只更新该目录索引（**唯一潜在优势**） |
| **新建子目录** | 不影响索引文件位置；下轮全量 JSON 自然含新路径 | 新目录是否 **新建空索引**？空索引 upload 与否、consume 是否扫描空目录——规则变复杂 |
| **删除空目录** | 无索引文件留在已删目录 | 目录索引文件成为 **孤儿**（KB/本地残留 `.openclaw-sync-map.json`） |
| **目录 rename/move** | 索引文件仍在 mapping **根**，不动；JSON 内 path 键随 reconcile 更新 | 目录索引文件跟着目录 **一起 move**，或 move 后路径与索引文件位置 **不一致**，需额外 relocate 逻辑 |
| **文件 rename（同目录）** | 更新 JSON 内键即可 | 更新该目录索引内键即可（两者相当） |
| **跨目录 move** | 同一 JSON 内改键 | 需 **两个** 目录索引各改一份，且两次 upload |
| **与 SyncEngine 隔离** | 1 个旁路文件，不进 `filePatterns` / `sync_file_state` | **每个目录** 多 1 个旁路文件；误配 glob 时污染面更大 |
| **点文件隐藏** | 根下 1 个 `.` 文件；`localFs.walk` 已 skip | 每个目录都有 `.` 索引；walk skip 仍有效，但 **目录枚举噪音** 增加 |
| **原子性 / 一致性** | 单文件代表 **同一时刻** 全 mapping 快照 | 多文件先后 upload，Pull 端可能读到 **半新半旧** 组合（notes 已更新、项目 未更新） |
| **失败重试（§5.2）** | 1 条重试链；失败则下轮整表重试 | 部分目录 upload 成功、部分失败 → **长期不一致**，对账难 |
| **bidirectional 覆盖** | 1 个文件被覆盖，语义清晰 | 多文件部分覆盖，Obsidian 合并后 **部分路径来自 A、部分来自 B** |
| **清空 DB 后 publish** | `uploadContent` 幂等更新 **1** 个文件 | 需对 **每个** 历史索引文件幂等更新，或产生大量重复索引 |
| **多 mapping** | 每 mapping 1 个索引，边界清晰 | 每 mapping × 目录数，爆炸 |
| **限流 / 429** | 每轮至多 +1 次写 API | 每轮 +N 次写 API，易触发 `maxRequestsPerMinute` |
| **日志与排障** | `[FileIndex] publish ok, fileCount=1234` 一行说清 | 需按目录打 N 条日志，用户问「为什么这条 path 没有 id」要查 **哪个目录索引** |
| **测试用例** | 增删改 rename、move 目录、清空 DB、失败重试 | 上述 × 多目录索引 + **交叉 move** + 部分失败 |
| **安全暴露面** | 1 个文件含全部 path+fileId | 攻击面相同（总信息量一样），但文件分散 **更难审计** |

---

#### 方案 B 唯一看似优势 — 增量更小 — 为何不成立

| 论点 | 反驳 |
|------|------|
| 「只改一个目录就只 upload 那个目录的索引」 | v1 已从 SQLite **全量生成** JSON，生成成本主要在 DB 读而非 JSON 大小；方案 A 用 **content hash** 相同则 skip upload，绝大多数轮次 **0 次** 索引 API |
| 「单文件太大」 | 万级 note 约 **数百 KB～1MB**（§5.5）；真正瓶颈是 **API 次数与一致性**，不是 JSON 字符串长度 |
| 「按需只读当前目录索引」 | Obsidian 插件常见需求是 **任意 note 的 fileId**（反向链接、批量操作），最终仍要 **全量 map**；分目录读只是把 merge 成本推给消费端 |

若将来 **>5 万条** 且 profiling 证明单 JSON 成为瓶颈，v2 可讨论按 **少量顶层目录**（如 3～5 个 shard）拆分——那是 **受控分片**，仍不是「每个子目录一个」。

---

#### 结构示意（Pull 端消费）

**方案 A（1 步）**

```
read localRoot/.openclaw-sync-map.json
→ map.files["notes/2024/foo.md"]
```

**方案 B（至少 2 步，目录 deep 时常更多）**

```
path = "notes/2024/foo.md"
dir  = "notes/2024"
read localRoot/notes/2024/.openclaw-sync-map.json   // 还要处理 index 随目录 move 的路径
→ map["foo.md"]  或 map.files["foo.md"]
// 若插件需要全 vault 索引，仍需递归 read 所有目录索引并 merge
```

---

#### 结论（v1 决策）

| | 方案 A 根目录全量 | 方案 B 每目录一份 |
|--|------------------|------------------|
| **推荐** | ✅ **采用** | ❌ 不采用 |
| **理由** | API 少、状态简单、原子快照、rename/move 友好、Obsidian 一次读表、与现有 `local_path` 模型一致 | 实现与运维复杂度随目录数线性恶化；一致性、重试、排障全面劣于 A；体积优势可忽略 |

**已确认**：v1 在 mapping **localRoot / 远端根** 各维护 **一个** `.openclaw-sync-map.json`，`files` 为整 mapping 的 `local_path → remoteFileId` 全量表。

### 3.3 上传 API 选型

原方案写 `uploadContent`；当前业务文件已改为 **分片上传 + saveFileByPath / updateFileVersion**。

| 选项 | 建议 |
|------|------|
| **uploadContent**（`folderName` + `fileName` + `projectId`） | **推荐**：同路径**幂等**（有则更新、无则新建）；响应 `fileId` 写入缓存 |
| 传 `updateFileId` | **可选优化**：DB 已有 `index_file_remote_id` 时可传，非必须 |
| FileUploader 全链路 | 过重，无必要 |

对索引 JSON（通常 < 1MB），上表仍适用。

实现时在 `fileIndexService` 内封装 `uploadContent` / `getDownloadInfo`，**不要**走 `SyncEngine.executePlan`。

## 4. 与现有同步逻辑的兼容性（原方案正确之处）

| 原方案论点 | 代码验证 |
|------------|----------|
| 不走 filePatterns | 默认 `**/*.md`；`.json` 本就不会进对账 ✓ |
| 点文件不参与本地扫描 | `localFs.walk` 对 `dirent.name.startsWith('.')` **直接 skip** ✓ |
| 不进 sync_file_state | 独立上传即可 ✓ |
| 不参与 rename/move | 不写入 file/folder state ✓ |
| 全量从 SQLite 生成 | reconcile 完成后 DB 路径已更新 ✓ |
| 内容相同不上传 | 合理，减少 API ✓ |

**Pull 端额外好处**：索引写在 `localRoot` 根目录且以 `.` 开头，即使用户误开 `filePatterns: **/*`，本地 walk 仍不会索引该文件。

## 5. 实现难点与风险

### 5.1 首次定位远端索引 fileId（**仅 Pull consume 需要**）

> **2026-05-25 修订**：Publish 侧**不需要**事先定位 fileId，见下文。

#### Publish（push / bidirectional 上传）

`uploadContent` 在 **相同 `projectId` + `folderName` + `fileName`** 下是**幂等**的：远端已有同名文件则原地更新，不会重复创建。

因此 **无论 DB 里有没有 `index_file_remote_id`**，publish 都可以直接：

```
uploadContent({
  projectId,
  folderName: remoteRootFolderPath,   // mapping 远端根路径
  fileName: '.openclaw-sync-map.json',
  fileSuffix: 'json',
  content: jsonString,
  // 不传 updateFileId 即可
})
→ 响应 fileId 写入 sync_mapping_state.index_file_remote_id（供 Pull 下载加速）
```

| 场景 | 是否需要事先 `getChildFiles` 找 id |
|------|-------------------------------------|
| 首次 publish | ❌ 不需要 |
| 清空 DB 后再 publish | ❌ 不需要（幂等更新已有文件） |
| 日常 publish | ❌ 不需要（可选传 `updateFileId` 作优化） |

#### Consume（pull / bidirectional 下载）

下载必须走 `getDownloadInfo(fileId)`，**没有 fileId 就无法下载**。因此 locate 只发生在 **Pull 端首次 consume 且 DB 无缓存** 时：

```
index_file_remote_id 为空？
  → getChildFiles(resolvedRootFileId)   // 根目录一层，按 name 匹配
  → 找到 → 缓存 id → getDownloadInfo → 写本地 .openclaw-sync-map.json
  → 未找到 → warn 跳过（Push 端尚未发布索引），不阻断主 sync
```

**为何不用 `listDescendantFiles`（v1）**：索引固定在 mapping **远端根目录**一层，`getChildFiles` 足够；全子树扫描过重，仅作 API 失败时的兜底。

#### 风险（修订后）

| 风险 | 说明 | 缓解 |
|------|------|------|
| Pull 首次无缓存 | 需一次 `getChildFiles` 拿 fileId | 找到后缓存；后续直接用 id |
| consume 时远端尚无索引 | Push 未开或未成功 publish | warn 跳过，不阻断主 sync |
| 根目录子项极多 | `getChildFiles` 列表变长 | v1 可接受 |

**结论**：原 §5.1 把 publish 也写成「要先 locate」是**过度设计**；v1 仅 **consume 冷启动**需要按名找 id，publish 一律直接 `uploadContent`。

### 5.2 索引与主同步的时序

| 场景 | 建议 |
|------|------|
| Push 主同步 `failed > 0` | **不上传索引**（避免传播不完整映射） |
| Push 主同步成功但索引上传失败 | **本轮内重试**（见下）；全部失败后**放弃本轮**索引上传，**不**影响主同步结果 |
| Pull 索引下载失败 | **不阻断**主同步；warn + 可选轻量重试（1～2 次） |

#### Push 索引上传重试策略（v1）

主 sync 已成功（水位已推进）后，在**同一轮** `runSync` 末尾执行 `publishIndex`：

```
publishIndex()
  ├─ 内容 hash 与上次成功上传相同 → skip（无 API）
  └─ 有变化 → uploadContent
        ├─ attempt 1..N（默认 N=3，与 KbApi MAX_RETRIES 一致）
        │     失败 → 指数退避（1s / 2s / 4s，与主 API 同量级）
        │     429 / 610012 → 走现有 RateLimiter 冷却后再试
        ├─ 成功 → 写 index_file_remote_id、index_content_hash
        └─ N 次均失败 → warn 日志，放弃**本轮**索引上传
```

**失败时的状态约束**（保证下轮可自动补发）：

| 字段 | 失败时 |
|------|--------|
| `index_content_hash` | **不更新**（下轮仍视为「待发布」） |
| `index_file_remote_id` | 仅在上传**成功**且响应含 `fileId` 时更新 |
| 主 sync 水位 / stats | 已成功的部分**不回滚** |

**日志示例**：`[FileIndex][test] publish failed after 3 attempts: API error …; will retry next sync`

**与主 sync 隔离**：索引 publish 抛错**不**让 `runSync` 整体失败；Web UI 状态可在 mapping 级增加 `lastIndexError` / `lastIndexOkAt`（Phase 4 可选）。

#### Pull consume 重试（简版）

`getDownloadInfo` / `getChildFiles` 失败：最多 **2 次**即时重试（无长退避），仍失败则 warn 跳过，主 sync 继续。

### 5.3 索引内容范围与 `files` 键格式

#### 导出范围

从 `sync_file_state` 导出时：

- 仅 `sync_status = 'done'` 且 `remote_file_id IS NOT NULL`
- 排除失败 / 进行中记录

#### `files` 的键：`local_path`（相对路径） vs 仅文件名

**结论：v1 使用 `local_path`（相对 mapping 根目录的路径），不用纯文件名。**

| 维度 | `local_path`（如 `notes/2024/foo.md`） | 仅 `fileName`（如 `foo.md`） |
|------|----------------------------------------|------------------------------|
| **唯一性** | 路径在 mapping 内唯一 ✓ | 不同目录同名文件**冲突**，后者覆盖前者 ✗ |
| **与 SyncEngine 一致** | 全链路 Map key、DB 主键语义均为 `localPath` ✓ | 需额外拼目录，与现有代码脱节 ✗ |
| **Obsidian 消费** | `file.path` / vault 相对路径直接查表 ✓ | 无法区分 `a/x.md` 与 `b/x.md` ✗ |
| **rename/move 后** | reconcile 已更新 `local_path`，下轮索引自然正确 ✓ | 文件名不变但目录变了 → **键丢失旧路径关联** ✗ |
| **Pull 端对齐** | 约定 `localRoot` = vault 根时，键 = Obsidian 相对路径 ✓ | 仅适用于根目录扁平 vault ✗ |

**为何不选远端 `relativePath` 单独作键**：在 mapping 设计下，同步完成后本地 `local_path` 与 KB 相对 mapping 根的路径**应对齐**；Push 端导出 `local_path` 即可，Pull/Obsidian 按同一套相对路径读索引，心智模型与 `sync_file_state` 一致。

**格式规范**（写入 JSON 前）：

- 使用 `canonicalizeRelativeSyncPath(local_path)`：正斜杠 `/`、无 leading slash、无 `.`/`..`
- 键 = 值侧路径语义；值为 `remote_file_id` 字符串
- 导出前按 key 字典序排序，便于 diff 与人工 diff

```json
"files": {
  "日常笔记/2024.md": "1234567890",
  "项目文档/架构设计.md": "9876543210"
}
```

**Obsidian 查表**：`map.files[file.path]`（`file.path` 为 vault 相对路径，且 vault 根 = mapping `localRoot`）。

可选扩展（非 v1）：增加 `remoteFolderId`、`contentHash` 字段供 Obsidian 优化。

### 5.4 安全与合规

- 索引含**全部同步路径 + fileId**，有 KB 读权限即可见
- 文档中保留「敏感路径评估」；v1 不做加密，v2 可考虑可选 AES + 共享密钥

### 5.5 体量

- 1 万文件 JSON ≈ 数百 KB～1MB，`uploadContent` 可接受
- \>5 万文件：v2 考虑 gzip + 分片或按目录拆分多个索引

### 5.6 Web 配置与迁移

## 7. 模块设计

```

  └─ runSync 后：publish（enableFileIndex + push/bidirectional + failed===0）
```

## 9. 对 Obsidian 插件的接口约定

消费端读取路径：

```
{vaultRoot}/.openclaw-sync-map.json
```

最小逻辑：

```typescript
const map = JSON.parse(await adapter.read(indexPath));
// file.path = vault 相对路径（vault 根须与 mapping localRoot 一致）
const remoteFileId = map.files[file.path];
```

**前提**：用户 Pull mapping 的 `localRoot` 与 Obsidian vault 根一致（或文档说明路径对齐规则）。

## 10. 不建议的做法

1. 把 `.openclaw-sync-map.json` 纳入 `filePatterns` 走普通同步 — 会引入自引用与 delete/upload 混乱  
2. 索引用 FileUploader 分片上传 — 实现复杂、收益低  
3. 为 v1 引入 `serverId` / 双开关 — 增加配置与文档成本，当前场景收益有限

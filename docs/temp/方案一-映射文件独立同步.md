# 方案一：本地文件 → 知识库 remoteFileId 映射文件独立同步

## 一、背景

同步服务部署在多台远程服务器上，各服务器将本地文件推送到知识库。用户在自己的电脑上从知识库拉取文件，但无法直接访问远程服务器的 SQLite 数据库，导致无法获知 `localPath → remoteFileId` 的映射关系。

需要一个机制让映射数据随同步链路自动流转：

```
服务器A → 知识库 → 用户本地
```

## 二、方案设计

### 2.1 核心思路

- 同步完成后，从 SQLite 全量读取当前 mapping 下的文件映射数据，生成 JSON 文件
- 映射文件**不走 SyncEngine 的普通同步流程**，由独立的上传/下载逻辑处理
- 通过配置开关 `enableFileIndex` 控制是否启用，每个 mapping 独立配置

### 2.2 为什么不走普通同步流程

| 问题 | 走普通同步 | 走独立逻辑 |
|------|-----------|-----------|
| filePatterns | 默认只匹配 `**/*.md`，需每台服务器改配置 | 完全独立于 filePatterns，零配置侵入 |
| 自引用 | 映射文件自身会出现在 sync_file_state，时序矛盾 | 不记录到 sync_file_state，无此问题 |
| SyncStats 污染 | 元数据计入正常统计 | 不影响同步统计 |
| 增量快速通道 | 映射文件变化与远端0变更逻辑矛盾 | 完全独立，互不干扰 |
| 文件夹移动 | 映射文件参与 rename/move 检测 | 固定在根目录，不参与任何检测 |

### 2.3 生成规则

- **文件名**：`.openclaw-sync-map.json`
- **位置**：固定在 `localRoot` 根目录
- **格式**：

```json
{
  "mappingId": "xxx",
  "serverId": "sz-prod-01",
  "generatedAt": 1716723600000,
  "fileCount": 42,
  "files": {
    "日常笔记/2024.md": "1234567890",
    "项目文档/架构设计.md": "9876543210"
  }
}
```

- `serverId`：从配置读取，标识服务器来源（多台服务器场景下用于区分）
- `files`：`key` = 相对 localRoot 的路径，`value` = 知识库 remoteFileId

### 2.4 内容更新策略

每次同步完成后：

1. 从 SQLite 全量读取 `sync_file_state` 中该 mapping 的所有记录
2. 过滤掉映射文件自身
3. 生成 JSON 内容
4. 与上一次生成的内容对比（字符串对比即可）
5. **内容相同则不写入**，避免无意义的文件变更和 API 调用

### 2.5 Push 端流程（服务器 → 知识库）

```
runSync() 完成
  ↓
判断 enableFileIndex 是否开启
  ↓ 是
从 SQLite 读取全量映射 → 生成 JSON 内容
  ↓
内容是否有变化？
  ↓ 是
调 uploadContent（folderName + fileName + projectId + content）
  · 同路径幂等：有则更新、无则新建；可不传 updateFileId
  · 有 index_file_remote_id 时可选择性传入 updateFileId 作优化
  ↓
上传成功 → 响应 fileId 写入 mapping_state.index_file_remote_id
```

### 2.6 Pull 端流程（知识库 → 用户本地）

```
runSync() 开始前
  ↓
判断 enableFileIndex 是否开启
  ↓ 是
从 mapping_state 读取 index_file_remote_id
  ↓ 有                       ↓ 没有（Pull 冷启动）
调 getDownloadInfo          getChildFiles(根目录) 按文件名查找
  ↓                         ↓ 找到 → 缓存 remoteId → getDownloadInfo
下载内容 → 写入本地           ↓ 未找到 → warn 跳过
  ↓
继续正常同步流程
```

**Pull 冷启动**：无 `index_file_remote_id` 时需 `getChildFiles` 在远端根目录按名找一次（不用 `listDescendantFiles` 全子树扫描）。Publish 侧无此步骤。

## 三、配置设计

### 3.1 SyncMapping 新增字段

```typescript
export interface SyncMapping {
  // ... 现有字段

  /**
   * 是否启用文件索引映射文件。
   * 启用后，同步完成时在 localRoot 根目录生成 .openclaw-sync-map.json，
   * 并通过独立通道上传/下载。
   * 默认 false。
   */
  enableFileIndex?: boolean;
}
```

### 3.2 SyncConfig 新增字段

```typescript
export interface SyncConfig {
  // ... 现有字段

  /**
   * 全局服务器标识，用于区分多台部署实例。
   * 写入映射文件的 serverId 字段，方便消费端识别来源。
   */
  serverId?: string;
}
```

### 3.3 sync_mapping_state 表新增字段

```sql
ALTER TABLE sync_mapping_state ADD COLUMN index_file_remote_id TEXT;
```

存储映射文件上传后的 remoteFileId，避免每次查找。

### 3.4 配置示例

```json
{
  "serverUrl": "https://kb.example.com/api",
  "appKey": "xxx",
  "serverId": "sz-prod-01",
  "syncDirection": "push",
  "autoSyncIntervalSec": 300,
  "mappings": [
    {
      "mappingId": "notes",
      "enabled": true,
      "localRoot": "D:\\notes",
      "remoteRootFolderPath": "OpenClaw/Notes",
      "enableFileIndex": true
    }
  ]
}
```

## 四、边界情况处理

### 4.1 文件夹移动/重命名

映射文件固定在根目录，不参与任何 rename/move 检测。每轮全量从 SQLite 重新生成，SQLite 中的路径已被 reconcileEngine 更新为正确状态。无论中间经历了多少次文件夹移动，最终映射文件一定准确。

### 4.2 多台服务器同名路径

通过 `serverId` 区分。消费端可按 serverId 过滤，知道某文件来自哪台服务器。

### 4.3 映射文件内容过大

文件数量在万级以内时，JSON 文件通常在几百 KB，知识库 API 可正常处理。如果文件数超过 5 万，可考虑分片或压缩。

### 4.4 安全性

映射文件包含所有同步文件的路径和 remoteFileId。推到知识库后，有该知识库访问权限的人都能看到。如果路径中包含敏感信息（人名、项目代号等），需评估风险，必要时可对内容做加密或路径脱敏。

## 六、风险与待确认项

1. **映射文件名**：`.openclaw-sync-map.json` 以 `.` 开头，各 OS 默认隐藏 — **已采用**
2. **多服务器同远端根**：固定文件名可能互相覆盖 — **已知、可接受**
3. **是否需要加密**：取决于路径是否含敏感信息；v1 不加密
4. **Obsidian 插件**：需自行读取 JSON 并接入业务（本仓库外）
